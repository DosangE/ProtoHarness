# 아트 요청서 — 다섯 트랙 장식 소품 (공통 킷 + 트랙 고유)

> 작성 2026-11-10, `docs/art-request-props`. 사용자 "아트 요청서 작성하자. 리소스 낭비를 막기 위해 비슷하게 공통으로 사용될 수 있는 것은 공통으로 사용하는 등 하자. 모든 맵에 대해 아트적 디테일 추가해보자".
> 같은 날 A1~A6 를 `gameplay-designer`(플레이)·`blender-artist`(제작) 에게 따로 판단시켰고(사용자 "A1~6에 대해 기획 에이전트와 아트 에이전트 둘에게 시켜서 판단해봐"), 그 결과를 보고 사용자가 정했다(6절). 두 에이전트가 찾은 요청서의 틀린 곳·빠진 곳은 이 판에 고쳤다(7절).
> **이 문서는 구현 승인이 아니다.** 킷마다 `blender-artist` 파견(승인 줄·브랜치 줄, `CLAUDE.md` §3-4)과 Unity 반영(§3-2 합의 요청서)을 따로 올린다.
> `blender-artist` 는 이 문서의 **한 킷 절**과 **2절 공통 규칙**을 받아 만든다. 절에 없는 치수·이름은 채우지 않고 멈춘다(`.claude/agents/blender-artist.md`).

## 1. 지금 장식이 만들어지는 방식 (코드에서 확인)

- 다섯 트랙 장식은 에디터 빌더가 코드로 짓는다: `Assets/_Project/Scripts/Editor/ChainRush/{FingerLanes,PalmCoast,Skyway,Stadium,SummitDrop}EnvironmentBuilder.cs`. 결과는 트랙별 장식 프리팹(`Assets/_Project/Prefabs/<트랙>Exterior.prefab`)이고 달리는 씬에 Additive 로 붙는다(`docs/ART_SKYWAY.md`).
- 소품은 Unity 기본 도형 세 개(상자·구·원기둥)에 팔레트 머티리얼을 하나씩 입혀 조립한다(`ExteriorKit.cs:14-16,31-60`). `Shape` 는 **메시 bounds 로 나눠** 원하는 m 크기로 늘리고(`ExteriorKit.cs:46-49`), 머티리얼은 하나만 넣는다(`:53`). 기본 도형은 bounds 가운데가 원점이라, 지금 모든 `Box`/`Shape` 호출의 위치 값은 **도형 가운데**다.
- SUMMIT DROP 만 원본 메시 두 개를 코드로 만든다: 소나무 잎 `ConeMesh`(`SummitDropEnvironmentBuilder.cs:806-822`, 쓰는 곳 `:426` 하나), 바위 `CragMesh`(`:824-833`, 쓰는 곳 `Rock` 의 `:449` 하나).
- 병합은 트랙마다 다르다.
  - SUMMIT DROP: 모든 그룹을 머티리얼별로 병합(`:165`, 함수 `:835-860`, 필터마다 머티리얼 하나만 읽음 `:840`).
  - SKYWAY: 지형과 외곽 도시만 병합(`SkywayEnvironmentBuilder.cs:378-379`, 함수 `:387`).
  - STADIUM: 관중석·지붕 면은 머티리얼별 버퍼에 직접 쌓는다(`StadiumEnvironmentBuilder.cs:253-`). 소품은 병합하지 않는다.
  - FINGER LANES·PALM COAST: 병합 호출 없음. 렌더러가 그대로 남고 정적 배칭 플래그만 붙는다(`ExteriorKit.cs:56`).
- 색은 트랙마다 `Palette("<트랙>", 이름, 색)` 으로 만든 단색 머티리얼이다(`ExteriorAssets.cs:47`). 같은 모양이 트랙마다 다른 색을 쓰는 구조가 이미 있다.
- 장식에는 콜라이더가 없어 시뮬·서킷 지문에 닿지 않는다(DECISIONS 2026-11-06 "select-tests: 장식 메시는 전체가 아니다"). 배치는 통로 검사를 통과해야 한다(SUMMIT `:156-161`) — 모양이 커지면 빌드가 실패한다.

**그래서 공유 방식은 "모양은 킷이 공유하고, 색은 트랙 팔레트가 고른다" 이다.** 킷 메시 하나 = 머티리얼 슬롯 하나 = 지금 `Box`/`Shape` 호출 하나를 바꾸는 단위다. 병합하는 트랙·안 하는 트랙 모두 그대로 쓴다.

## 2. 공통 규칙 (모든 킷)

| 항목 | 규칙 | 이유 |
|---|---|---|
| 파일 | 킷 하나 = `art-src/<Kit>/<Kit>.blend` + `<Kit>.fbx` 한 쌍. FBX 안에 이름 붙은 오브젝트 여러 개 | `CONVENTIONS.md` §1-3. 임포트·확인을 킷 단위로 한 번에 |
| 오브젝트 이름 | PascalCase, 이 문서 표의 이름 그대로 | Unity 에서 메시 하위 에셋을 이름으로 찾는다 |
| 머티리얼 | **오브젝트 하나에 슬롯 하나.** 슬롯 이름은 표의 역할 이름(`M_Rock` 등). 색은 확인용이고 Unity 에서 트랙 팔레트로 바뀐다 | 1절. `Shape` 가 머티리얼을 하나만 넣는다 |
| **피벗** | **모든 오브젝트: bounds 가운데.** (표지판 시험 제작의 "바닥 가운데" 와 다르다 — 그것은 통째 소품이었고, 킷은 기존 `Box`/`Shape` 호출을 바꾸는 부품이다) | 지금 호출의 위치 값이 도형 가운데라서(1절) 메시만 바꾸면 위치 식이 그대로다 |
| 치수 | m. 표의 치수는 **튀어나온 부분(보강대·턱·문틀·뿌리)까지 포함한 bounds 전체**다 | `Shape` 가 bounds 로 나누므로, 튀어나온 만큼 본체가 작아진다 — 본체 비율은 표 설명을 따른다 |
| 크기 종류 | **실제 크기**: 스케일 1 = 그 크기, Unity 에서 균일 스케일만. **단위 크기**: 코드가 배치마다 늘린다(비균일). 표에 어느 쪽인지 적었다 | 단위 크기 오브젝트는 늘린 모습으로 시안을 본다(5절 1) |
| 앞면·축 | Blender **−Y**(Front 뷰에서 보이는 면) → Unity **+Z**. Blender +Z → Unity +Y. Blender +X → Unity −X 쪽으로 보인다(앞에서 보면 같은 모습). 표의 "긴 축" 은 Unity 축으로 적고 Blender 축을 괄호로 붙였다 | DECISIONS 2026-11-09 "Blender 시험 제작" 측정 |
| 180° 돌려 쓰는 것 | 거울 모양을 따로 만들지 않는다. 판의 법선 축(Unity Z)으로 180° 돌려 쓴다(`>` → `<`, 왼쪽 덧문 → 오른쪽). 그래서 **위아래 대칭**이어야 한다 | 음수 스케일을 쓰지 않기 위해. 돌리면 위아래도 뒤집힌다 |
| 길이가 바뀌는 것 | 다리·기둥·집 벽·지붕 판·굴뚝·배치마다 폭이 다른 판(SKYWAY 막다른 베이 판 `Skyway…:880-882`)은 **만들지 않는다**(코드 상자로 남긴다) | 늘리면 모양이 찌그러진다 |
| 색이 둘인 것 | 색마다 오브젝트를 나눈다(A6). 나눈 조각은 **겹치지 않게** 같은 경계선을 공유한다(위에 덧붙이지 않는다) | 덧붙인 면은 멀리서 깜빡인다(z-fighting) |
| 얇은 판 | 한 면짜리 면을 쓰지 않는다. 깃발·잎처럼 얇은 것도 두께(표 값)를 준다 | Unity 기본 셰이더는 뒷면을 그리지 않을 수 있다(확인 못 함) — 두께로 피한다 |
| 스타일 (A1) | 로우폴리 + **플랫 셰이딩**, 텍스처·UV 없음, 모서리만 살짝 죽인다(베벨은 모디파이어 그대로 두어도 FBX 가 적용해 내보낸다) | 지금 단색 팔레트·도형 장식과 이어진다 |
| 폴리곤 (A2) | 크기 등급 **S ≤ 200 / M ≤ 600 / L ≤ 1500** 삼각형(모디파이어·bmesh 베벨 적용 뒤 수). 표에 오브젝트마다 등급을 적었다. **목표는 상한의 1/3~1/2 이고, 표의 "추정" 은 베벨 전 계산이라 목표가 아니다** | K4 실측: 베벨이 삼각형을 두세 배 늘렸다(추정 40~160 → 실제 136~276) |
| 내보내기 | `blender-artist` 정의의 프로젝트 기본 FBX 설정 그대로 | |
| 확인 | `look` 으로 앞·옆·위 각 1장 + 1 m 기준 상자와 나란히 1장. 단위 크기 오브젝트는 **표의 "늘려 쓰는 크기"로 늘린 모습**도 1장 | 크기·늘림 착오를 Blender 에서 먼저 잡는다 |

## 3. 공통 킷 (1차) — 만드는 순서대로

순서는 사용자 결정(A3·A4): **K4 → K3 → K1 → K5 → K2 → K7 → K6**, 한 킷씩 5절 1→5 를 끝내고 다음으로 간다. 순서는 `blender-artist` 의 제안(만드는 기법이 같은 것끼리)이다.
"쓰는 곳" 은 지금 그 모양을 코드 도형으로 만드는 줄이다. Unity 반영 때 이 줄들이 킷 메시를 쓰게 바뀐다(따로 합의). "추정" 은 `blender-artist` 의 계산이고 측정이 아니다.

- 코드가 높이의 0.42 만큼 올려 놓고(`:448`) 무작위로 기울여 돌린다(`:450`). 바닥이 묻히는 것을 전제로 아래쪽은 단순해도 된다.
- 지금 원본 `CragMesh` 는 정점 8개를 공유해 부드러운 셰이딩이다(`:827-830`). 플랫(A1)으로 바뀌면 각진 모습이 된다 — 시안에서 같은 바위를 플랫·부드러운 셰이딩으로 나란히 1장 보인다(A1 비교, `blender-artist` 제안).
- **결과 (2026-11-10, `feature/art-rockkit`, DECISIONS 같은 날 "K4 바위")**: 3종을 시드로 고른다(`Hash(seed * 59)`). 첫 플레이에서 "기존 바위와 뭔 차이가 있는지 모르겠다", "공중에 떠있는 바위도 있다". 떠 있는 것은 메시가 아니라 배치 탓이었다 — 중심 한 점의 지면만 읽어 30개 중 29개가 비탈 아래쪽으로 3~33 m 떠 있었다. 바위마다 메시 사본의 아래 40% 를 정점마다 그 밑 지면까지 끌어내려 밑동이 비탈을 따르게 했고, 높이의 60% 넘게 늘려야 하는 낭떠러지 자리에는 놓지 않는다(30 → 27개). 두 번째 플레이 "괜찮다". 이전/새 모습 비교 렌더는 같은 크기·머티리얼로 찍었다(DECISIONS 같은 항목).
- **다음 킷에 적용할 것**: ① 단위 크기로 10~30배 늘려 쓰고 도로에서 20 m 넘게 떨어진 소품은 모양을 바꿔도 달리는 중에 차이가 잘 보이지 않는다 — 효과는 길가 소품·큰 실루엣에서 먼저 본다. ② 비탈에 놓이는 소품(K3 나무 줄기 포함)은 중심 한 점의 지면만 읽으면 뜬다. 바닥이 넓은 것은 K4 와 같은 밑동 맞추기를 쓴다.

## 5. 한 킷의 진행 (각 단계 따로 승인)

1. **시안** — `blender-artist` 가 그 킷의 오브젝트를 만들고 `look` 으로 보여 준다(2절 "확인"). 사용자가 고르거나 고칠 점을 말한다.
2. **FBX 내보내기** — 같은 에이전트에 이어서. `art-src/<Kit>/`.
3. **Unity 연결 (§3-2 합의 요청서)** — 첫 킷(K4)에서 `ExteriorKit` 에 킷 메시를 이름으로 읽는 함수(새 공개 API)를 정하고, 다음 킷부터는 그것을 쓴다. 역할 슬롯 → 트랙 팔레트 대응, 빌더 교체 줄, 정리 후보였던 "복사 → 임포트 → 확인 → 렌더" 도구도 여기서 정한다.
4. **재빌드 → 전후 렌더 → 사용자 플레이 확인** — 렌더는 같은 카메라 3곳(출발·트랙 중간·결승 직전). 빌드 로그 원문(개수·정점 수·검사 PASS)을 남긴다. 장식 프리팹 재빌드는 fileID 가 새로 나와 diff 가 크다(HANDOFF 2026-11-06 "장식 재빌드"). 씬·프리팹 브랜치는 한 번에 하나(§9-2).
5. **그 킷을 쓰는 나머지 트랙** — 트랙 하나씩.

1~2 는 Blender 가 하나라 직렬이다(`blender-artist` "동시 사용 금지").
