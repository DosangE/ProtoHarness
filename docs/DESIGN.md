# Chain Rush 3D 러닝액션 — 설계와 로드맵

> **상태: 초안, 합의 대기.** 이 문서의 어떤 항목도 아직 구현 승인이 아니다. (`CLAUDE.md` §3)
> 현재 구현은 `docs/ARCHITECTURE.md`, 결정 이력은 `docs/DECISIONS.md`. 여기는 **앞으로** 만 다룬다.
> 작성 2026-10-01, 같은 날 개정(최종 목표 C 확정). 코드 근거는 `파일:줄` 로 적었고, 읽지 못한 파일에 대한 주장은 "확인 못 함"으로 표시했다.

## 1. 목표

**최종 목표: 카트라이더식 서버 권위 공유 월드 레이스.** 유한 트랙(기록 경쟁)과 무한(생존) 두 모드, 최대 8인, PC+모바일. 한 월드에서 여러 플레이어가 같이 달리며 서로 앞지르고, 서로를 방해한다. (2026-10-01 사용자 확정)

가기 위한 순서:

1. **무한 모드를 게임으로 완성한다.** 지금은 "무한 전투 프로토타입"이다.
2. **ScriptableObject 로 수치와 콘텐츠를 데이터화한다.** 프로젝트 최초의 SO 다.
3. **오프라인에서 결정성과 구조 분리를 먼저 확보한다.** (시드, 고정 틱, 입력 추상화, 플레이어별 상태 분리, 리플레이)
4. **서버 권위 멀티플레이를 최소 형태에서부터 쌓는다.**

## 3. 목표 구조 (방향만)

공유 월드 레이스에서 가장 먼저 바뀌어야 하는 것은 **"플레이어 한 명의 게임"을 "여러 레이서가 있는 레이스"로 분리**하는 것이다.

- **레이서 상태 / 레이스 상태 / 표현을 분리한다.**
  - 레이서 상태: 위치·속도·체력·그래플·쿨다운. 서버가 소유하고 클라가 예측한다.
  - 레이스 상태: 시드, 진행도, 순위, 아이템 박스 같은 공유 사실. 서버가 소유한다.
  - 표현: 카메라, HUD, 오디오, 체인 시각물, 관절 애니메이션. 클라 전용, 로컬 플레이어는 예측값을, 원격은 보간값을 본다.
- 현재 `ChainRushGame` 은 위 셋을 한 클래스에서 다 한다 (`ChainRushGame.cs:11-24`, 상태 + 오디오 + 시각물).
- 서버 권위 + 클라 예측이므로 **입력 → 고정 틱 시뮬 → 상태** 가 서버·클라에서 같은 코드로 돌 수 있어야 한다. (C2, C5, C9)

## 4. 단계

### P0. 기반 정비 (구현 전 합의 필요)

- **SO 도입.** 후보는 셋이며 모두 `Assets/_Project/Data/` 에 둔다.
  - `RunRules` — 체력, 무적 시간, 공격 쿨다운 (C6)
  - `EncounterTuning` — 경고·진입·공격창·비행·회수 시간, 조우 간격 곡선 (`EnemyDirector.cs:18-22,152`)
  - `CourseLayout` — 발판 길이, 갭 길이, 변형 목록 (`EndlessCourse.cs:12-13`)
- **첫 SO 이므로 형식을 먼저 합의한다** (§2). 제안: `[CreateAssetMenu(menuName = "ProtoHarness/ChainRush/<이름>")]`, 필드는 `[SerializeField] private` + 읽기 전용 프로퍼티, 값 검증은 `OnValidate()` 에서 `Debug.LogError`.
- **EditMode asmdef 와 첫 EditMode 테스트.** SO 검증, 순수 로직용. 이것도 첫 사례다.
- 씬·프리팹 수정은 §0 에 따라 에디터에서 한다. 기존 에디터 빌더가 SO 참조를 연결하도록 바꾸는 방식이 후보.

### P1. 무한 모드 완성 + 레이스 전제 확보

- **시드 기반 코스.** `(seed, 거리) → 구간 변형` 이 결정적이어야 한다. 시스템 `Random` 이 아니라 시드 하나로 재현되는 자체 생성기. 커브·오르막·내리막을 포함한 코스 설계는 `docs/COURSE.md` (초안, 2026-10-04).
- **게임 로직을 고정 틱으로 옮긴다** (C2). 렌더 보간은 표현 계층에만 둔다.
- **입력 추상화** (C5). 입력 → "의도(이동, 점프/그래플, 공격)".
- **레이서 상태 분리 시작** (§3). 우선 한 명이어도 `RacerState` 를 `ChainRushGame` 에서 꺼낸다.
- **적 다변화** (C7), **점수·결과 화면**, 로컬 최고 기록.

### P2. 기록과 리플레이 (네트워크 없음)

> **2026-10-08 구현·검증 (결과는 `DECISIONS.md` "P2")**: 입력 기록·재생(`Control/`)과 상태 트레이스 비교로 같은 시드 + 같은 입력이 같은 머신·같은 에디터에서 **비트 단위로 같은 런**을 만든다는 것을 서킷·절차 코스에서 확인했다. 파일 저장·고스트 표시는 아직 아니다. 아래 항목은 구현 전 계획이다.

- 같은 시드와 같은 입력 로그가 같은 결과를 내는지 **리플레이 테스트**로 증명한다. 이 테스트가 곧 결정성(C2, C3, C9)의 조기 경보다.
- 고스트 재생은 레이스 UI·상대 표시의 선행 실험이 된다.
- P3 의 가장 큰 위험(재현성)을 네트워크 없이 먼저 확인하는 단계다.

### P3. 서버 권위 레이스 — 최소 형태부터

C 는 한 번에 만들지 않는다. 각 단계가 **직전 단계 위에서 돌아가야** 하며, 단계마다 §3-2 합의를 올린다.

| 단계 | 내용 | 완료 기준(안) |
|---|---|---|
| **C1 최소 레이스** | 2인, 방해 없음. 서버가 시뮬, 클라는 입력 전송 + 예측 + 보정. 같은 PC·LAN 에서 | 두 클라가 같은 서버 월드에서 달리고 서로를 본다. 입력 지연이 있어도 조작이 끊기지 않는다 |
| **C2 추월·충돌** | 앞지르기, 몸 충돌, 밀치기, 슬립스트림 같은 위치 기반 상호작용 | 충돌 결과가 서버·클라에서 일치한다 |
| **C3 방해 요소** | 아이템(공격·방어·가속), 그래플로 상대를 끌어당기거나 방해하는 규칙 등 | 요소별 SO 정의, 서버가 판정 |
| **C4 확장** | 4–8인, 매치메이킹, 서버 인프라, 부정행위 대응, 순위·결과 | 인원·지연 조건에서 안정 |

**B(각자 월드 계산) 는 중간 산출물로 만들지 않는다.** B 의 "클라가 계산하고 결과만 전송" 은 C 의 "서버가 계산" 과 구조가 반대다. 겹치는 부분(시드·고정 틱·입력 추상화·로비/UI 개념)은 P1·P2 에서 이미 확보한다. **A(비동기 고스트·랭킹)** 는 P2 의 연장이라 선택 사항이다.

**네트워크 패키지·전송·서버 방식은 이 문서에서 정하지 않는다.** C1 착수 전에 후보를 실제 패키지 소스로 조사하고(§4-1) manifest 변경을 승인받는다.

## 5. 순서와 이유

```
P0 SO·EditMode  →  P1 무한 모드 + 시드·고정 틱·입력 추상화·레이서 상태 분리  →  P2 리플레이/결정성  →  P3 C1 → C2 → C3 → C4
```

- P1 의 시드·고정 틱·입력 추상화·상태 분리는 C 의 **필수 전제**다. 먼저 하지 않으면 P3 에서 무한 모드를 다시 뜯어고친다.
- P2 의 리플레이 테스트가 재현성을 자동으로 증명한다. 재현성이 깨지면 예측·보정이 안 되므로 가장 싼 조기 경보다.
- 이 문서의 승인은 각 단계의 구현 합의를 대신하지 않는다.

## 6. 확정된 요구 (2026-10-01 사용자)

| 항목 | 내용 |
|---|---|
| 모드 | 쿠키런 + 카트라이더를 참고한 **세 가지**. ① **무한(쿠키런식)**: 오래 살아남기 + 점수를 먹는다. ② **속도전(카트라이더식)**: 단순 랩타임. ③ **아이템전(카트라이더식)**: 아이템을 활용한 경쟁이 주. 세부 규칙은 미정(§8) |
| 인원 | 최종 최대 **8인** |
| 상호작용 | **아이템**과 **접촉**(추월·충돌·밀치기). **기본 그래플은 지금처럼 유지**한다(갭을 건너는 이동 수단). **다른 유저를 대상으로 하는 그래플**(카트라이더 **자석**처럼 당김)은 **아이템으로만** 가능하다 |
| 플랫폼 | **PC + 모바일** (같은 서버, 크로스 플레이 전제) |
| 서버 | 서버 지식 없음 → §7 에서 조사 후 추천 |

영향:
- **그래플은 두 가지로 갈린다.** ① **환경 그래플**: 지금 그대로. 코스의 앵커·갭 구조와 `GrappleController`(앵커 선택·줄 길이 제약) 유지 (`ARCHITECTURE.md` §4). ② **대인 그래플**: 상대를 대상으로 당기는 동작. **아이템 효과로만** 존재한다. 서버가 판정하는 상호작용이므로 P3 C3 의 첫 후보다. 두 동작이 같은 체인 시각물(`ChainVisual`)을 공유할지는 구현 시 결정.
- **모바일은 입력 추상화(C5)의 필수 근거**가 된다. 터치 입력을 같은 "의도"로 변환해야 한다. 8인 동시 표시의 성능 예산도 별도로 잡아야 한다 (`Assets/Settings/Mobile_RPAsset.asset` 이 이미 있다).
- **무한 모드를 멀티로 하면 C4(월드 원점 이동)가 다시 문제다.** 유한 트랙은 월드가 고정이라 해당 없음. §8 질문 2.

## 7. 서버·네트워크 방향 (조사 2026-10-01)

> 서비스 상태·가격은 자주 바뀐다. 아래는 웹 조사 결과이며 **출처 등급을 표시했다**. 선정 시점에 공식 문서로 재확인한다 (`CLAUDE.md` §4-1).

### 7-1. 서버 형태 — 판단: **전용 서버(headless Unity 빌드)**

| 형태 | 설명 | 이 프로젝트에서 |
|---|---|---|
| **전용 서버** | 서버만 따로 돌아가는 빌드. 모두가 클라이언트 | 서버 권위 + 8인 + 방해 요소 + PC/모바일 크로스에 맞다 |
| 호스트 겸 클라 | 한 플레이어의 기기가 서버를 겸함 | 호스트가 모바일이면 부담이 크고, 호스트에게 지연 이점이 생겨 경쟁에 불공정 (**판단**, 미실측) |
| 서비스 일체형 | 외부 서비스가 서버 로직까지 호스팅 | 상호작용 규칙을 직접 짜야 하는 이 게임에는 맞지 않을 가능성 (확인 못 함) |

**개발 중에는 서버 비용이 0이다.** 내 PC 에서 서버를 띄우고 에디터·빌드로 접속해 테스트한다. 호스팅은 출시 직전에 정하면 된다.

### 7-2. 네트워크 라이브러리 후보

| 후보 | 확인된 것 | **확인 못 한 것 / 위험** |
|---|---|---|
| **Netcode for GameObjects (NGO)** | Unity 공식 패키지. GameObject·MonoBehaviour 방식이라 **현재 코드 구조와 가장 가깝다.** Windows·macOS·Linux·iOS·Android 지원 (공식 문서 요약, 1차). 2026-03-31 Multiplay 호스팅 종료에도 NGO·Relay·Lobby·Matchmaker 는 계속된다 (벤더 블로그, 2차) | **클라이언트 예측·롤백을 얼마나 내장하는지 확인 못 했다.** 공식 페이지 요약에 해당 내용이 없었고, 검색 요약 하나가 "물리 예측이 내장돼 있지 않다"고 했으나 출처 신뢰도가 낮다 |
| **Photon Fusion 2** | 전용 서버·호스트 겸 클라 토폴로지 지원, **예측·롤백·스냅샷 보간 내장**이라고 설명한다 (Photon 문서 요약, 2차) | **상용 서비스**: 가격·동시접속 한도·모바일 빌드 조건 확인 못 함. 벤더 종속 |
| **Netcode for Entities** | 예측 루프가 **내장**돼 있고 서버에서 같은 시뮬을 돌린다 (공식 문서 요약, 1차) | **DOTS/ECS 로 전환해야 한다.** 현재 MonoBehaviour·CharacterController 코드를 사실상 전면 재작성 (**판단**). 이 프로젝트에는 비용이 크다 |

### 7-3. 호스팅 (출시 직전 결정)

- **Unity Multiplay 호스팅은 2026-03-31 종료**됐다 (Gameye 블로그, 벤더 2차 자료). 대안으로 Rocket Science Group, Edgegap, Gameye 가 거론된다. 가격(예: Gameye `$0.07/vCPU/hr`)은 **벤더 주장**이며 검증 안 됨.
- 선택은 개발 중 필요 없다. 지금 정하지 않는다.

### 7-4. 추천 (서버를 모르는 사용자 기준)

1. **서버 권위 + 전용 서버**로 간다. 개발 단계에서는 **내 PC 에서 서버를 띄운다.** 호스팅은 나중.
2. **지금은 네트워크 라이브러리를 정하지 않는다.** 대신 P1 에서 **시뮬 코어를 엔진·네트워크 비의존**으로 만든다 (고정 틱 + 입력 → 상태 함수 + 레이서 상태 분리, §3). 이 구조는 어떤 라이브러리를 고르든 필요하다.
3. **C1 직전에 소규모 스파이크로 확정한다.** 후보 **NGO vs Photon Fusion 2**, 판정 기준은 "2인이 지연 100ms 에서 이동·점프가 끊기지 않고 서로 일치하는가". Netcode for Entities 는 코드 전면 재작성 때문에 **후보에서 제외**하는 것을 권고한다.
4. 기울기: 구조가 가장 가깝고 벤더 종속이 없는 **NGO 를 기본**으로 하되, 스파이크에서 예측·보정 구현 비용이 크면 Fusion 2 를 택한다. **이 기울기는 예측 지원 정도를 확인하기 전의 판단이므로 스파이크 결과가 우선한다.**

> 근거 부족을 숨기지 않는다: NGO 의 예측 지원 정도는 이번 조사에서 **확인하지 못했다.** 스파이크 전에 Unity 공식 NGO 문서(예측·anticipation 관련 장)를 직접 읽는다.
